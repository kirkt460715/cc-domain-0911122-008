# 日历采集计划设计

## 1. 基本立场
当地日期只是业务标签，真正的覆盖范围落在 UTC 时间轴。每个营业日窗口由两部分确定：

- 覆盖区间：当地 `D 日 business_start` 到 `D+1 日 business_start`，解析成一对确定的 UTC 秒；
- 触发时刻：当地 `D 日 trigger`，同样解析成 UTC 秒，可因夏令时出现 0、1 或 2 个。

所有区间都是左闭右开 `[start,end)`，持久化为 epoch 秒；展示时再转 ISO-8601 UTC。

## 2. 夏令时语义
解析单个挂钟时间得到三种状态（`energyflow/collection/localtime.py`）：

| 状态 | 含义 | 策略 |
| --- | --- | --- |
| `unique` | 只对应一个 UTC 时刻 | 直接使用 |
| `gap` | 春季跳时中不存在的挂钟 | `skip`：不触发，窗口放弃并写原因；`shift-forward`：移到缺口后第一刻 |
| `ambiguous` | 秋季回退中重复的挂钟 | `first`（较早的夏令时一次）、`second`（较晚的标准时一次）、`both`（两次都展开为窗口） |

营业日界限本身也可能落在缺口或重复时刻：缺口边界取缺口起点并备注，重复边界取第一次出现并备注。每次解释都在 `collection_notes` 留下结构化原因（如 `nonexistent_local_time_skipped`、`boundary_inside_spring_gap`、`ambiguous_local_time_dropped`）。

## 3. 计划版本与窗口不变性
计划每次修改都新增一条不可变版本（`collection_plans` 带 `revision` 与哈希摘要），旧版本置 `active=0`。窗口物化时把当时的 `revision` 固化进自身记录与载荷：

- 已物化（含正在执行、已完成、已放弃）的窗口永远不被新版本重新解释；
- 新版本只影响尚未物化的营业日；
- 操作员可通过 `collect.plan_versions` 与窗口上的 `revision` 看到旧版未完成窗口仍按旧版处置。

## 4. 窗口状态机
`planned → ready/running → partial → collected`，旁路 `abandoned`、`skipped`：

- `skipped`：节假日，不产生来源请求；
- `abandoned`：触发被 skip、整日维护、`latest` 追赶放弃的旧日期、或操作员明确放弃的缺口；
- 运行失败（网关 503/不可达）置 `failed`，租约过期也会回收，下轮重试；
- 只有“维护排除段之外的全部区间都被成功运行的覆盖并集拥有”才进入 `collected`。

## 5. 区间所有权与覆盖证据
- 维护段在物化时折算成 UTC 排除段，tick 从不请求这些时段，也不计入缺失；
- 每个成功运行记录其请求区间与来源确认的 `coverage`；窗口的已拥有区间是所有成功运行覆盖的并集；
- 正常触发与人工补采共用同一套所有权：补采只申请未拥有的缺口段，已采区间不会重复请求，重复读数在读数入口按身份复用而非覆盖；
- 来源 `complete=false`/`coverage=null` 时不拥有任何区间，未采范围始终如实显示为缺失，绝不会标成完成；
- 预算（`max_runs`、`max_readings`）耗尽即停，状态保留在原处，下个 tick/补采从第一个未拥有区间继续。

## 6. 追赶策略
- `all`：物化区间内每个未完成营业日逐日补齐；
- `latest`：只采最近一个营业日，更早的未完成日期显式置 `abandoned` 并写 `latest_catchup_older_day_abandoned`；
- 操作员确认无法恢复的缺口用 `collect.abandon_gap` 放弃，缺口区间与原因留痕，汇总里计入 `abandoned_seconds` 而不是被掩盖。

## 7. 持久化与注入
表：`collection_plans / collection_windows / collection_runs / collection_notes`，均带规范 JSON 与 sha256 摘要，状态变更进既有 `audit` 哈希链；`Store.integrity` 与 `verify_audit` 可核对。时钟（`collection.runtime.Clock`）、来源客户端（`SourceClient`，默认走回环 HTTP）均可注入，演示通过 `python3 -m energyflow.collection_demo` 运行，报告写入 `var/collection_demo_report.json`。

## 8. 服务动作
统一经 `EnergyService.dispatch` 暴露 `collect.*`：`create_plan / get_plan / list_plans / plan_versions / preview / materialize / windows / window / notes / tick / backfill / abandon_gap / runs / coverage`。
